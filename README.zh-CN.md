```text
d = 3·b + (t + 1)        b = d // 3        t = d % 3 - 1

d ∈ {0..5}   b ∈ {0,1}   t ∈ {-1, 0, +1}
```

> **这是一个存储容器，不是加速器，也不是数值类型。**
> `d` 是**码元**，不是 base-6 数字。它上面不定义算术。

---

## 这份报告是什么

这份报告只问一个问题：

> 如果二进制引擎和三进制引擎要共享存储，有哪些数据模型和编码值得考虑？

报告覆盖四种数据模型（T、I、X、S）、九种具体编码，以及存储、解码、随机
访问、稀疏 gather、选择性读、完整性和信息利用率；还包括场景权重、带宽
模型、权重敏感性、真实 GPT-2 无损性检查和故障注入。

Dual6 是其中一个实现点，报告不声称它全胜。在实测载荷上，等权综合评分
的第一名都是 `int8`，Dual6 第二。X 是另一类候选：一种面向“一个值、两个
原生视图”的存储格式，只有当共享状态的协调成本足够高时，它的冗余才值得。

## 命名

用这个编码存下来的模型，就是**一个 `.p6` 文件**——`llama-3-8b.p6`、
`bitnet-2b.p6`，而不是一堆分片加一堆 sidecar。

后缀取 `6`，因为 6 是第一个**完全数**（1 + 2 + 3 = 6），也正是这个编码的来源：
**2 态 × 3 态 = 6 态**。

中文名是**二生三**，取自《道德经》“道生一，一生二，**二生三**，三生万物”：
二（二进制）生三（三进制），就装在这一个码元里。

## 四种数据模型

同一个 6 态码元可以承载四种不同契约，不能混用。

#### 数据模型：T、I、X、S

| 模型 | 含义 | 每元素信息 bit | Dual6 存储 | 利用率 | 可互推 | 写语义 |
|---|---|---:|---:|---:|:-:|---|
| **T** 纯三值 | 每元素一个平衡三值，没有 bit 通道 | 1.585 | 1.6 bpw | **99.1%** | 否 | 更新一个 trit（局部） |
| **I** 独立双通道 | 每元素两条独立通道 | 2.585 | 2.6 bpw | **99.4%** | 否 | 独立更新 bit 或 trit |
| **X** exact-dual | 同一个整数 `N` 的两种展开 | 1.000 | 2.6 bpw | **38.5%** | 是 | 重算 `N` 中间码元块 |
| **S** 影子投影 | 一个 trit + 派生 bit，如 `b = (t != 0)` | 1.585 | 2.6 bpw | **61.0%** | 否 | 更新 trit，重算派生 bit |

- **T** 是纯三值场景。
- **I** 是唯一让 6 态码元信息最优的模型。
- **X** 把同一个整数 `N` 的 base-2 数字和平衡三进制数字装进同一个码元；
  两个视图都能还原 `N`。它是一种存储格式，但不是压缩格式；冗余换来的是
  两个原生视图。
- **S** 的第二通道没有新信息，作为反例保留，不推荐。

#### 九项计分指标

评分卡使用九项实测指标：

1. 每元素存储 bit
2. 编码时间
3. 解码时间
4. 随机访问时间
5. 稀疏 gather 时间
6. 选择性读取字节
7. CRC / 完整性标志
8. 单对象标志
9. 每元素操作数

综合评分再加第十项：信息利用率。它是十项等权的描述性聚合，不是普适排名。

#### 九种编码

trit 载荷上测量九种编码：fp16 稠密、int8 稠密、TQ1_0、TQ2_0、6 态 3-bit
槽、三种 Dual6 布局和两份独立数组。其中六种还能承载独立的 `(bit, trit)`
双通道。X 和 S 没有完整实测 codec，单独评分：解码路径用 native 实测，其余
计时指标标记为代理。

## Dual6 作为一个实现

Dual6 直接实现 **I**：`mux(bits, trits)` 把两条独立通道装进一条码元流。
它通过可选的 `dual6.exact_dual` 实现 **X**。**S** 只作为不推荐的反例记录。

### 布局

| 布局 | 码元 | 字节 | 使用位数 |
|---|---:|---:|---:|
| 交错 | 5 | 13 | `D = Σ dᵢ·6ⁱ` |
| `D6-64` | 24 | 8 | 63 / 64 |
| `D6-128` | 48 | 16 | 125 / 128 |
| `D6-40` | 40 | 13 | 104 / 104 |

| 双平面块 | bit 平面 | trit 平面 | 合计 |
|---|---:|---:|---:|
| `D6-64-DP` | 3 B | 5 B | 8 B |
| `D6-128-DP` | 6 B | 10 B | 16 B |
| `D6-40-DP` | 5 B | 8 B | 13 B |

### 帧

| 帧 | 头部 | 完整性 | 用途 |
|---|---|---|---|
| `D6P0` | 17 B | — | 最小帧 |
| `D6P1` | 20 B | CRC32 | 单双平面流 |
| `D6P2` | 33 B | CRC32 | dtype、flags、块元数据 |

`D6P2` 的两个选项：

| 选项 | 效果 |
|---|---|
| `FLAG_OMIT_BIT_PLANE` | 去掉 bit 平面——纯三值载荷从 2.6 bpw 降到 **1.6 bpw** |
| `layout = 1` | 压缩 bit 平面——每块一个标志位，只有含 1 的块才存 bitmap |


### X：一个值，两个原生视图

```python
from dual6 import exact_dual

symbols = exact_dual.encode_number(42)
assert exact_dual.read_binary(symbols) == 42
assert exact_dual.read_ternary(symbols) == 42
```

X 的约束是全局的，不是每个码元内部的：

```text
Σ b_i·2^i = Σ t_i·3^i = N
```

所以它的信息利用率约为 `1 / log2(6) = 38.5%`：每个码元名义上能装 2.585
bit，但 X 只用它承载 1 bit 新信息，外加同一个 N 的冗余投影。写入时重算
受影响的中间码元块；读取时不做跨进制转换。

## 测了什么、怎么测

主评分卡有 **15 行**（9 个 trit 载荷、6 个 dual 载荷）和 **19 个原始列**。
除特别说明外，时间都是每元素。时间、字节、操作数越低越好；完整性和单对象
是 0/1 标志。

原始时间来自同一台机器、同一套 harness。绝对数字不可迁移，排序和曲线形状
可以。native 解码是 Rust 微基准；稠密格式使用 `memcpy` 下限，并标有 `†`。
这个下限对稠密格式偏乐观，因此比较方向对 bit-packing 有利。

### 为什么比较多种编码

存储格式是一组权衡，不是一个数字。一个格式可以在字节上赢、在解码上输，
却仍然适合“一个可校验、可原子替换的单文件”。评分卡展示权衡，不宣布唯一
赢家。

（21301 B）。

#### 权重敏感性

每组载荷用 5,000 个随机整数权重向量、三种确定性方案抽样。trit 载荷上，

#### 物理成本模型

时间本身不是带宽模型。对每种编码：

```text
effective_ns = max(decode_compute_ns, bytes_per_element / bandwidth)
```

低带宽时，紧凑格式因内存主导而赢；高带宽时，解码计算主导，稠密格式赢。
有用的是交叉点，不是某个绝对赢家。

| 带宽 (GB/s) | trit 赢家 | 有效 ns | dual 赢家 | 有效 ns |
|---:|---|---:|---|---:|
| 1 | Dual6 双平面 / Dual6 双平面（trit-only） / 两份独立数组 | 0.448 | Dual6 双平面 / 两份独立数组 | 0.448 |
| 3 | int8 稠密 | 0.333 | Dual6 双平面 / 两份独立数组 | 0.448 |
| 10 | int8 稠密 | 0.100 | int8 稠密 | 0.200 |
| 30 | int8 稠密 | 0.035 | int8 稠密 | 0.067 |
| 100 | fp16 稠密 / int8 稠密 | 0.035 | int8 稠密 | 0.035 |
| 300 | fp16 稠密 / int8 稠密 | 0.035 | fp16 稠密 / int8 稠密 | 0.035 |
| 1000 | fp16 稠密 / int8 稠密 | 0.035 | fp16 稠密 / int8 稠密 | 0.035 |

  <sub>有效 ns vs 链路带宽。约 1–3 GB/s 以下存储赢，约 30 GB/s 以上计算赢。</sub>
</p>

#### 模型级无损性

可选的 GPT-2 实验把权重量化成三值，存入 Dual6 帧再读回。它只验证
**存储无损性**：

| 范围 | 编码元素数 | Dual6 bpw | 权重精确 | logits 精确 | Top-1 一致 | 备注 |
|---|---:|---:|---|---:|---:|---|
| transformer 线性层 | 84,934,656 | 1.604 | 是 | 是 | 100% | embedding/LayerNorm/bias 保留 fp16 |
| 全部 2-D 权重 | 124,318,464 | 1.604 | 是 | 是 | 100% | 全部 2-D 权重量化 |

朴素 absmean 三值化会毁掉原模型：线性层范围的 top-1 一致率是 3.1%，全部
2-D 权重是 0%。这是量化结果，不是存储结果。模型权重不在仓库里。

#### 故障注入

对四种容器、三种更新协议做故障注入后发现：静默损坏由**校验和 + 原子
rename** 决定，而不是字节布局。原地同尺寸覆盖在 64 KiB 以下不可见，
512 KiB 开始撕裂，之后继续增长：

| 载荷 | 静默读 / 200 | 静默比例 |
|---:|---:|---:|
| 4 KiB | 0 | 0.0% |
| 64 KiB | 0 | 0.0% |
| 512 KiB | 3 | 1.5% |
| 2 MiB | 34 | 17.0% |
| 8 MiB | 53 | 26.5% |

<p align="center">
  <img alt="fault size" src="benchmarks/charts/fault-size.png" width="600"><br>
  <sub>原地覆盖下，静默损坏读随载荷尺寸增长。</sub>
</p>

同样的结论适用于无关格式：普通 GGUF 套一层 manifest 也能得到同样保护。
**这不是容器本身的性质。**

### 局限

- 绝对时间是机器相关的，没有同一套 harness 和同一台机器就无法复现。
- X/S 的证据是混合的：解码是 native，其它计时是代理。
- 最大载荷是 8 MiB；故障数据来自合成容器，不是生产模型服务。
- 驱动 I 的逐元素侧通道**目前是假设性的**：今天的格式故意避免对齐的
  第二通道，因为那很贵。
- exact-dual 编码器仍是 Python 逐位实现；native 编码性能是后续工作。

## 报告发现了什么

**它并没有更快，这个仓库应当以这种方式被阅读。**

| 问题 | 答案 |
|---|---|
| 哪些数据模型信息最优？ | **T（99.1%）** 和 **I（99.4%）**；**X** 是 38.5%，**S** 是 61.0%。只有 I 让 6 态码元信息最优。 |
| X 是压缩格式吗？ | **不是。** X 是面向共享状态的存储格式：用冗余换一条流、无副本同步、读取零进制转换。它该和“两份原生副本 + 同步协议”比，而不是和 `int8` 比密度。 |
| 独立的第二通道值多少？ | **2.6 bpw** vs T 的 1.6，溢价 **62.5%**；只有真的有人读第二通道时才值。 |
| Dual6 更快吗？ | 不。trit-only 模式与 `TQ1_0` 持平：**1.60 bpw / 59.2 ns** vs 59.3 ns；稠密 `int8` 解码快得多。 |
| 最可迁移的结果是什么？ | 故障注入：静默损坏由**校验和 + 原子 rename**决定，而不是字节布局；在这台机器上从 64 KiB 到 512 KiB 之间开始出现。 |

活下来的有三样：

1. **T 模型与现有打包持平**：**1.60 bpw / 59.2 ns**，同时帧可以附加 CRC32
   和单对象头。对纯三值载荷来说，这是一次便宜的完整性校验。
2. **压缩 bit 平面在 bit 通道是聚集掩码时划算**：5% 密度下省 **−25% 到
   −33%**，而周期散射反而贵 1.5%。判据是全零块占比，不是密度。
3. **最有用的结果不是这个编码。** 静默损坏由校验和 + 原子 rename 决定，
   与字节怎么打包无关；而且只在超过某个尺寸阈值后才出现（本机是 64 KiB
   到 512 KiB 之间）。这条结论对任何格式都成立。

所以结论是一张地图，不是冠军：**T** 用于纯三值，**I** 用于独立侧通道，
**S** 不推荐。**X** 是目标不同的存储格式：当两个原生读取端反复消费同一个
值时，它才是值得验证的混合时代候选。评分表可以给它排序，但不能判断协调
成本的节省是否值得它的冗余。

## 实际可能适用的场景

四种条件让 Dual6 值得考虑。每一条都写明“什么情况下它就不对”——一个声称
什么都能装的容器，其实什么都装不了。

**1 · 三值权重旁边挂一条逐元素侧通道** —— `D6P2` 双平面

三值主值 + 逐元素标志位（离群点、剪枝、“该用高精度副本”），同一个 kernel
在同一遍里读两者。一条顺序流，没有指针跳转，没有第二个文件会失步。掩码
聚集时 `layout 1` 再省 **−25% 到 −33%**。

<p align="center">
  <img alt="compacted bit plane vs mask structure" src="benchmarks/charts/mask-structure.png" width="600"><br>
  <sub>同样 5% 密度、五种排列、每种 5 次重复。聚集掩码省 25–33%；周期散射贵 1.5%。</sub>
</p>

*什么时候不对*：两个通道不是逐元素对齐的。今天的格式基本都避免对齐的
第二通道，正是因为它贵。**这个场景目前是假设性的**：容器为它准备好了，
不代表它已经存在。

**2 · 纯三值模型，但想要一个文件、一次校验** —— `D6P2`，
`FLAG_OMIT_BIT_PLANE`

落在 **1.60 bpw、59.2 ns/元素**，与 `TQ1_0`（1.60 / 59.3）持平，另外白得
CRC32 和单对象帧。适合慢介质与小机器：一次 `open`、一次 `mmap`、一次校验。

<p align="center">
  <img alt="compacted bit plane vs mask density" src="benchmarks/charts/sparse-plane.png" width="600"><br>
  <sub>密度扫描：掩码越稀收益越大，超过约 10% 后收益消失。</sub>
</p>

*什么时候不对*：数据本来就快。单帧加载并不更快——最好情况等价，多轮重复
下稳定慢约 2%。在 NVMe 或 cache 驻留场景里，帧头是纯开销。

**3 · 边服务边热更新** —— 任何帧 + 协议

**这不是容器的性质。** 对四种互不相关的容器做故障注入表明：静默损坏由
**校验和 + 原子 `rename`** 决定，与字节怎么打包无关。普通 GGUF 套一层
manifest 能得到同样的保护。

*测量到的是曲线形状*：64 KiB 以下看不到撕裂，512 KiB 是 1.5%，2 MiB 是
17.0%，8 MiB 是 26.5%。只要你原地覆盖模型文件，不管什么格式，超过
512 KiB 就已经暴露。

**4 · 加载器要写在 C / C++ / Rust 里** —— `D6P1` / `D6P2`

固定头部给出平面偏移；bit 平面可直接寻址，trit 平面就是现成的 5-trit/byte
打包，现有三值 kernel 不用改。嵌入成本是一次头部解析。

*“零拷贝”要小心用*：bit 平面可以直接用，**trit 平面仍然需要解包**。

### 明确不适用的地方

- 纯三值推理、无逐元素元数据 → 用 `TQ1_0`；
- 能整体进 cache → `int8` 的解码快一个数量级；
- 跨层混合精度、MoE 路由表、KV cache 布局 → 通道不对齐，本文测量不适用；
- 通用压缩 → 这是存储容器，不是编解码器；
- 把 X 当成普通原生存储的替代品 → 它设计上就是冗余的，只有当双原生读取
  或共享状态协调值得这份冗余时才适用。

## 展望

真正开放的问题不是再调一次编码评分，而是：混合二进制—三值执行是否会让
“共享状态本身”变得昂贵。如果会，X 是第一个值得验证的候选；如果不会，
这个容器就只是一个对无人提问的问题给出的、测试完备的答案。

## 独立实验

X 的三方案成本对比——一条共享码元流、两份原生副本、单副本加转换——刻意
不放进这份报告。它保存在独立的 `x-hybrid-experiment` 分支，并作为单独
压缩包分发。它不会在这里增加 CSV、测试或评分。

## 状态

**待命，不是废弃。** 容器能用、有测试；前提未经验证之前不再加新功能。

前提很窄：二进制引擎和三值引擎**在同一遍里读同一个元素**。今天它只成立
一半——BitNet 这类三值模型存的是三值，算的是 FP16，bit 通道没有消费者。
两个信号会改变这一点：

1. 出现一种公开的模型格式，其**逐元素**元数据与权重一起被读取
   （不是 per-tensor scale，也不是稀疏索引）；
2. 三值**运算**原生执行，而不是先解包成浮点。

## 范围

**属于容器层**——码元、序列/布局/块打包、帧、错误码、单通道适配。

**不属于**——数值语义解释、量化、dtype/shape 元数据、张量算子、任何模型
格式连接器。容器只负责搬运字节，不解释它们。
